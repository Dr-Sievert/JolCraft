# JolCraft

`AGENTS.md` is a byte copy of this file for other agents; keep the two identical.

Ground-up rewrite of the mod for **Minecraft 26.1.2 / NeoForge 26.1.2.122**, Java 25, ModDevGradle 2.0.148, Gradle 9.8.2, Groovy build scripts. Mod id `jolcraft`, root package `net.sievert.jolcraft`. The tree holds the module skeleton, the primitives and six composites, no systems or features yet: the tier types, the stereotypes, the `log`, `language`, `config`, `network`, `attachment`, `data`, `sound`, `schedule`, `recipe`, `loot`, `advancement`, `menu`, `command`, `capability`, `stat` and `registration` primitives, the architecture test, the game-test scene adapter and the datagen mod. The 1.21.1 tree lives in `old/` as reference. **The rules are in `design/module-map.md`; this file says where things are and how to run them.**

## Commands

```bash
./gradlew compileJava compileGametestJava compileDatagenJava   # fast correctness check
./gradlew test                              # JUnit under FML: the architecture test and unit tests
./gradlew runData                           # datagen into src/generated/resources, cleared first; game dir run/data; fails on incomplete data; build, runClient and runGameTestServer refuse to run without it
./gradlew runGameTestServer                 # every @Scene, headless, game dir run/gametest (what CI runs)
./gradlew runClient                         # dev client in run/; runClient2 starts a second player "Dev2" in run/client2
./gradlew build                             # test + jar in build/libs
```

CI (`.github/workflows/build.yml`) runs `runData`, then `runGameTestServer`, then `build` on JDK 25. Gradle uses the configuration cache and an 8 GB heap. `check` also compiles the gametest and datagen source sets, so a broken dev mod fails the build. An IDE run configuration skips the generated-resources guard and the clearing that the Gradle run tasks carry.

## Source sets

| Source set | Holds | Loaded by | Ships |
|---|---|---|---|
| `main` | the mod, `net.sievert.jolcraft` | every run | yes |
| `test` | `ArchitectureTest` and unit tests, JUnit with FML bootstrapped and only the main mod loaded | `test` | no |
| `gametest` | dev-only mod `jolcraft_gametest`: the scene adapter, the scenes, the dev mod's own bin block and container block entity, and in `src/gametest/resources` the small data pack the scenes read (a recipe, loot modifier and advancements of the dev mod's own) and the bin's blockstate | client, server and gameTestServer runs | no |
| `datagen` | dev-only mod `jolcraft_datagen`: the contributors and providers | the data run (`--mod jolcraft,jolcraft_datagen --flat`; without `--flat` NeoForge nests each mod's output in its own folder) | no |

Each run's `loadedMods` in `build.gradle` names exactly the mods it loads. The dev source sets get the modding dependencies from `addModdingDependenciesTo`; the integrations' jars reach their runtime classpath only, never their compile scope.

## Layout

- `JolCraft.java` — the composition root: builds every module by hand in its constructor, registers content, listeners and the primitives that register once (registration, attachment, sound, recipe, loot, advancement, menu, capability, stat and network on the mod bus; config on the mod container; schedule, command, the ledger and the recipe sync on the game bus; the result composite on the mod bus). Builds the mod's `ModLog`; the two dev mods are composition roots of their own and build theirs.
- `module/` — `Module` and the tier annotations `@Primitive`, `@Composite`, `@ModSystem`; a module's `id()` is read from its annotation. `module/primitive/<id>/`, `module/composite/<primitive>/`, `module/system/<feature>/`, each with an optional `client/` sub-package. Primitives so far: `module/primitive/log` (`Log`, `ModLog`), `module/primitive/advancement` (`Advancement`, sharing the game's simple name, `ModAdvancement`, and the `TriggerKey` handle: `of(id, instanceCodec)` for a kind of criterion the mod's features fire, declared while the module is built and registered once by the root into the trigger registry; `key.fire(player, matcher)` grants the matching criteria, `key.criterion(instance)` puts the kind into an advancement in datagen; `advancement.has(player, id)` and `grant(player, id)` ask and complete by id; advancements are data written by `AdvancementContributor` through `Advancements.Writer`, whose `shown(...)` titles and describes under `Advancement.title(id)` and `description(id)`, which datagen demands English for), `module/primitive/attachment` (`Attachment`, `ModAttachment`, and the `AttachmentKey` handle: `of(id, fallback)` then `saved(mapCodec)`, `synced(streamCodec)` which goes to every player who sees the holder (NeoForge consults its per-player predicate on updates only and the initial sync on tracking ignores it, so there is no owner-only variant and a player's own business travels as a network payload), `keptOnDeath()`; a module declares its keys while it is built, the root registers once at `RegisterEvent`, and the key reads and writes any holder with `get`, `isSet`, `set`, `update`, `reset`, or hands the game its `type()`; values are immutable, a change is a new value, and `set` syncs when the key is synced), `module/primitive/language` (`Language`, `ModLanguage`, and the `LanguageKey` value: Dictionary words joined with dots, the game's category first where the game has a convention, the mod's namespace first for its own text; `text(...)` gives the translatable component, the English lives in datagen) `module/primitive/data` (`Data`, `ModData`, and the `DataKey` handle: `of(id, fresh, codec)` for a `SavedData` the module owns, `serverWide()` for one instance in the server's storage instead of one per level; a module declares its keys while it is built, nothing registers since the game creates saved data on first ask, and the key reads with `get(level)` or `get(server)` and changes with `update(level, change)`, which marks the data dirty; an undeclared key refuses to be read), `module/primitive/loot` (`Loot`, `ModLoot`, and the `LootKey` handle: `modifier(id, mapCodec)`, `condition(id, mapCodec)` or `function(id, mapCodec)` for a kind the mod adds to the data pack's loot vocabulary, declared while the module is built and registered once by the root into the modifier-serializer, loot-condition or loot-function registry; the kind's class answers `codec()` with the key's; `loot.roll(level, table, params)` rolls a table of the data pack with the modifiers applied; the `Shape` value names a context's keys, required and allowed, so one shape both validates data at load (`shape.check(user)`, `codec.validate(shape.validator())`, the game's own check, naming a key the data reads that the shape lacks) and builds the context the data is fired with (`loot.context(level, shape, [random,] params)`; `shape.listValidator()` for a codec of lists, refusing a missing key by the shape's name; a key beyond the shape is carried, as NeoForge allows); datagen's `LootContributor.modifiers(LootModifiers)` writes the mod's global loot modifiers), `module/primitive/recipe` (`Recipe`, `ModRecipe`, the `RecipeKey` handle and the `Recipe.Custom` contract: a module's recipe is a record implementing `Recipe.Custom<Input>` with `matches` and, for an item result, `assemble`, the rest answered for a kind outside the recipe book; `RecipeKey.of(id, mapCodec, streamCodec)` is declared while the module is built, the root registers once and the game gets the kind's type, serializer and recipe-book category under the id; `key.find(level, input)` and `key.all(level)` read the level's data pack; `recipe.sync(gameBus)`, attached once by the root, asks the game to send every declared kind's recipes to a joining player, which the game no longer does unasked, for the JEI bridge; the `ItemInput` value is one item a recipe takes, the game's predicate with an unbounded count and a `Fate` (consume, damage or keep, with an amount or an inclusive range rolled on application), `matches(stack)` pure on both sides and `fate.apply(stack, level, holder)` paying it, nothing from a creative holder; datagen writes a recipe with `Recipes.Provider.add(id, recipe)`, which first runs `key.check(registries, recipe)`, the round trip through the kind's codec, so what the codec refuses fails `runData` and not the first login; the game's `Recipe` class is named in full where it must be), `module/primitive/schedule` (`Schedule`, `ModSchedule` over one package-private `Queue` per running server: `after(server, ticks, task)` and `every(server, interval, task)` give a `Task` to cancel, each task is due at an absolute tick count so a delay is the same wherever in a tick it is scheduled, tasks run on the server thread at the end of a tick in scheduling order, a repeating task counts from the tick it ran in so a lagging server never bursts, a stopped server's tasks are dropped and it takes no more, and a task that throws is reported through the `Failure` the root adapts from `Log` while the rest still run; the root attaches it to the game bus once), `module/primitive/stat` (`Stat`, sharing the game's simple name, `ModStat`, and the `StatKey` handle: `of(id)`, `shownAs(formatter)`; declared while the module is built, registered once by the root into the custom-statistic registry; `stat.award(player, key, amount)` and `value(player, key)`; named under `stat.<namespace>.<path>`, which datagen demands English for; the old offline award queue is not here, it is the `ledger` composite over `stat` and `data`), `module/primitive/sound` (`Sound`, `ModSound`, and the `SoundKey` handle: `of(id)`, `heardWithin(blocks)` for a fixed range; a module declares its keys while it is built, the root registers once at `RegisterEvent`, and the key plays on the server with `play(level, at, source, volume, pitch)`, `play(entity, volume, pitch)` (everyone in range, the entity included, nothing from a silenced one) or `playFor(player, ...)`; a client level plays nothing; a ranged key raises the volume sent so a client hears the whole range, since the game attenuates over 16 blocks per unit of volume; every sound shows the subtitle `subtitles.<namespace>.<path>`, which datagen's `Sounds` sets on every definition and `Translations` demands English for), `module/primitive/capability` (`Capability`, `ModCapability`: a module declares providers for block entities of a type, entities of a type or stacks of items while it is built, the types given as suppliers so the mod's own holders serve, the root registers once at `RegisterCapabilitiesEvent`; looking a capability up stays the game's own calls), `module/primitive/command` (`Command`, `ModCommand`: a module declares `Tree`s, each a Brigadier literal built with the game's command build context, while it is built; the root attaches once to the game bus and every tree is registered at `RegisterCommandsEvent`; trees sharing a root literal merge, so modules hang branches under the mod's name), `module/primitive/config` (`Config` with its `File` kinds, `ModConfig`, and the `ConfigKey` handle: flag, whole, real, text or choice, path from Dictionary words, English comment, fallback; declared into a file while modules are built, registered once by the root, read live with `get`, which answers the fallback before the file is loaded; NeoForge's own `ModConfig` class is used only inside the implementation, by its full name; every setting and section carries the translation key `<mod id>.configuration.<path>`, `ConfigKey.translation(namespace, words)` being the one formula; the words title, button, tooltip, warning and section are refused because the screen derives keys from them, and a path may not be a section of another's; a STARTUP setting loads when the root registers the files, keeps its first value until a game restart, and reading it earlier is an error, as is reading a key never declared once the files are built; `config/client/ConfigScreen` is the client bootstrap that gives the mod NeoForge's config screen from the mod list, registered only when settings exist), `module/primitive/menu` (`Menu`, `ModMenu`, and the `MenuKey` handle: `of(id, clientSide)` with how the client builds its copy from the window id, inventory and the server's data, declared while the module is built and registered once by the root into the menu registry; `key.open(player, title, serverSide, data)` opens it on the server with the module's own dependencies and writes the client's data; the menu class passes `key.type()` to its constructor; `menu/client/ClientMenu.screen(modBus, key, screen)` is where a module's client bootstrap gives the menu its screen), `module/primitive/network` (`Network`, `ModNetwork`: a module declares each payload with its direction, `toServer(type, codec, handler)` with the handler run on the server's main thread with the sending player, `toClient(type, codec)`; the root registers once under the mod's version, so client and server on different versions refuse to connect; sending is the game's `PacketDistributor`; `network/client/ClientNetwork.handle(modBus, type, handler)` is where a module's client bootstrap gives a clientbound payload its handler, and a client without one refuses to start naming the payload) and `module/primitive/registration` (`Registration`, `ModRegistration`: custom and datapack registries declared by modules and attached to the mod bus by the root once; the `Ids` helper builds identifiers, registry keys and tag keys from Dictionary words with an explicit namespace; the `Dispatch` helper builds a codec over a registry of kinds, a field naming the kind and the kind's codec reading the value, resolving the registry by key through the game's root registry only when the codec is first used, so a record's constant codec may name a custom registry a module declares). A primitive may not depend on another, so a primitive that must say something declares a small contract the root adapts from `Log` rather than taking `Log` itself.
- `module/composite/` — the composites, each a `@Composite` class in the folder of the primitive it extends, built from primitives only: `composite/schedule/Action` (a multi-tick transaction for an actor: ordered `Step`s on the actor's server, a `Running` handle to cancel or ask, and a recovery that runs once when the action ends early by cancel, by losing the actor or by a step that throws), `composite/language/Feedback` (telling a player: `tell` into chat, `show` over the hotbar, each with a `SoundKey` variant that plays for that player alone; takes `Language` and `Log`), `composite/attachment/Cooldown` (cooldowns on entities that survive a save: a `Cooldown.Key` per cooldown declared while a module is built, kept as a saved attachment holding the game time it ends at; `ready`, `remaining`, `start`, `clear`; takes `Attachment` and `Log`), `composite/stat/Ledger` (statistics for a player who may be offline: a `Ledger.Book` per module declared while it is built, naming the statistics it may award; `award(server, book, playerId, key, amount)` awards at once when the player is online and otherwise writes the award into the book, a server-wide saved data, from which that player's next login grants it; `waiting` counts what a player has coming; takes `Stat`, `Data` and `Log`, attached by the root to the game bus once), `composite/loot/Result` (data-described yields rolled against a loot context, for any system: a root declares its `YieldKinds` once under its own namespace, two custom registries of kinds and hooks the composite fills at `RegisterEvent` with its own four kinds, `ItemYield` (a loot pool), `EntityYield`, `SoundYield` and `EffectYield`, and every `YieldKind` and hook a module declares while it is built; a `Yield` validates itself against a `Shape` and `roll`s values without acting; `result.apply(yields, context)` asks every named `ResultHook` to agree, rolls, runs the hooks on each value and answers a `Delivery` the system acts on; `YieldKinds.codec()`, `listCodec()`, `choice()`, `single(kindCodec)` and `streamCodec()` are what a host embeds, a kind's bare codec never, since only these check the hook ids, built lazily over the registries so a record keeps them as constants; takes `Loot`, `Registration` and `Log`, attached by the root to the mod bus once), `composite/capability/Inventory` (items counted, taken and given against a holder's item handler, found when an operation runs: a `Holder` is a player or one of their hands, reached through the game's player inventory wrapper, or an entity or a block, reached through the capability lookups, each a value a system builds per call; `count(holder, predicate)` and `has` sum the slots the holder takes from, a player's main slots and offhand and never the worn armor, a hand its one slot; `give(holder, stacks)` inserts stacking the holder's own way, a player's through the game's place-back order and a hand's into that slot first, never changes the given stacks, skips empty ones, and drops the overflow at the holder after the commit, a player's tossed and targeted at them with no pickup delay as `/give` does, answering what was dropped as copies; every operation runs on the server thread, and a give and a pay each open their own root transaction and are all or nothing while counting and matching are pure; `exposeBlockEntity(type)` declares a module's container block entity under `Capabilities.Item.BLOCK` through `capability`, the root registering once; `match(holder, inputs)` matches the recipe primitive's `ItemInput`s against the holder, pure: per input in order, the first resource in index order whose total, less what earlier inputs claimed (a consume its largest amount, a damage or a keep one item), covers the fate, one resource per input and no backtracking, answering a `Match` whose stacks a host puts into its loot context; `pay(match)` applies the fates in one root transaction, the coverage checked again, every consume rolled through `Fate.apply` on a scratch stack and extracted, every damage extracting its one item, a shortfall answering false with nothing changed, then each damage's copy worn through `Fate.apply` and put back in its slot, crafting remainders given back, the overflow dropped after the commit; `take` is match then pay; design in `design/inventory.md`; takes `Capability` and `Log`).
- `module/system/` — the systems: a `@ModSystem` class in `module/system/<id>/` with its `@Content` beside it and its datagen contributors under `datagen/module/system/<id>`; none yet. The shared systems in `design/module-plan.md` come first, and the first feature brings the mod's first items and its first hand-made assets under `src/main/resources`.
- `stereotype/` — `@Implementation`, `@Value`, `@Handle`, `@Contract`, `@Helper`, `@Event`, `@Bridge`, `@Internal`, and the mod-only `@Content` (registry declarations), `@Keys` (a system's handle constants: the `RecipeKey` or `YieldKinds` a record names before the system exists, public static final handles only; a `RecipeKey` is declared to `Recipe` by the system's constructor, the mod's one `YieldKinds` to `Result` by the root) and `@Actor` (classes the game creates; they read data and post events, never reach a module).
- `util/text/` — `Dictionary` (every word used in an id, key or path) and `ModString` (joins them). `util` depends on the JDK alone.
- `src/test/java/.../ArchitectureTest.java` — the ten rules of the module map over ArchUnit, reading the compiled class directories (`jolcraft.main.classes`, `jolcraft.gametest.classes`, `jolcraft.datagen.classes`, set by the test task through a tracked `CommandLineArgumentProvider`, so a change in any of them re-runs the test). Rules 1 to 9 read the `main` classes alone; the dev mods are held to rule 10 only. The test first asserts that its import holds the mod; after that a rule whose selection is still empty is allowed to be vacuous. One rule checks the root itself: it reaches every `@Implementation`, `@Content`, `@Composite` and `@ModSystem` class, so nothing declared stays unwired.
- `src/gametest/java/net/sievert/jolcraft/gametest/` — `JolCraftGameTests` (entry), `scene/Scene` (the annotation), `scene/SceneRegistry` (finds every `@Scene` method through `ModFileScanData.getAnnotatedBy`, registers one test function per method in the game's test-function registry and one test instance per method at `RegisterGameTestsEvent`; ids are the scene's place in snake case, `system/trade/trade_scenes/offers_match`, or `example_scenes/<method>` for the adapter's own; shape and values are validated at discovery, finding no scene fails the run, and a scene that adds players must set `isolated = true` to get a batch of its own, and `addPlayer` refuses one that does not), `scene/TestScene` (arena, ticks, named checks, `onEnd`, players; owns its cleanup through a `GameTestListener` on `helper.testInfo`), `scene/TestPlayer` (a real mock `ServerPlayer` snapped to the arena, ticked and chunk-fed by the scene; `runCommand`, `received()`, `chat()`, `survival()` since a fresh one is creative; bundles are unpacked), `scene/PacketRecorder` fed by the one mixin in `mixin/` (config `jolcraft.gametest.mixins.json`). `ExampleScenes` are the adapter's own scenes; module scenes go under `gametest.module.<tier>.<folder>` (rule 10).
- `src/datagen/java/net/sievert/jolcraft/datagen/` — `JolCraftDatagen` (entry, listens to `GatherDataEvent.Client`), `Contributes` + `Contributors` (scan discovery; a contributor names its module's folder and sits in `datagen.module.<tier>.<folder>`), `contribute/*Contributor` (one interface per data kind: recipes, English text, models, tags, loot and loot modifiers, sounds, data maps, datapack registries, advancements), `provider/*` (one provider per kind over NeoForge's, opening the helpers contributors need), `Completeness` (the registry walk) and `Handmade` (exemptions by name and per registry: block models, item models, block loot, entity loot, each checked against its file and its registry entry). `runData` creates the datapack-registry entries first, under the mod's namespace, then fails on any item or block without a model, any block without a loot table, any entity type vanilla expects one for (those without `noLootTable()`; an empty table is fine), any item, block, entity type, mob effect, attribute or creative tab without a name, any config setting or section without a label for the config screen (`Translations.add(ConfigKey, label)`, `Translations.section(label, words)`; the screen's title and per-file texts are written by the provider), any sound event without a definition or without the English of its subtitle, any shown advancement without the English of its title and description, and any statistic without the English of its name, and any `LanguageKey` constant declared in a `@Value` class without its English (found through the mod's scan data). Recipe contributors get `Recipes.Provider` with vanilla's helpers opened; tag contributors can copy block tags to item tags.
- `src/main/templates/META-INF/neoforge.mods.toml` — expanded by `generateModMetadata` from `gradle.properties` and the enabled integrations. No `modLoader`, `loaderVersion` or range keys in 26.1.
- `integrations.properties` — optional mod integrations (JEI, Jade): Gradle artifacts per mod and the optional `[[dependencies]]` entry. `<name>.enabled=false` drops a mod from both. Code touching an integration API is a `@Bridge` behind a `ModList` guard.
- `src/main/resources` — hand-authored assets only; `src/generated/resources` is gitignored datagen output. Never hand-edit a generated JSON.
- `old/` — the complete 1.21.1 tree, not compiled; its layout map is `old/CLAUDE.md`.

## Verifying framework behaviour

Decompiled sources exist after any Gradle run. Vanilla with NeoForge's patches: `build/moddev/artifacts/minecraft-patched-26.1.2.122-sources.jar`. NeoForge's own classes: `~/.gradle/caches/modules-2/files-2.1/net.neoforged/neoforge/26.1.2.122/<hash>/neoforge-26.1.2.122-sources.jar`. FML (scan data, mod loading): the `net.neoforged.fancymodloader:loader` sources jar in the same cache. Check semantics there instead of guessing, for example:

```bash
unzip -p build/moddev/artifacts/minecraft-patched-26.1.2.122-sources.jar net/minecraft/gametest/framework/TestData.java
```

Renames and changes against the 1.21.1 code met so far: `ResourceLocation` is `Identifier`; `Entity.getServer()` is gone (go through `level().getServer()`); the packet listener's `send` takes a `ChannelFutureListener`; `GameTestHelper.testInfo` is public; game tests are registry-based (`TEST_FUNCTION` plus `RegisterGameTestsEvent`), and `neoforge.enabledGameTestNamespaces` no longer exists.

Mixins name their targets with `@Desc` and class literals (`@Inject(target = @Desc(value = "send", args = {Packet.class, ChannelFutureListener.class}), ...)`), never with a descriptor string: javac checks the types, and the Minecraft Development plugin (1.8.11) cannot resolve descriptor strings in this 26.x project and flags them.
